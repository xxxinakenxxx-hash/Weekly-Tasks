## 1. 目的（ユーザー確定要求　2026-10-21）

ユーザーは今後、週間分析JSON・朝ブリーフJSONを「作らない・コピーしない・貼らない・目視チェックしない」。JSONの生成から Sheets 反映までを自動化し、ユーザーの作業を「画面で見る・直す・確定する」だけにする。2つの貼付欄（週間分析用・朝ブリーフ用）をユーザーが取り違える事故（2026-10-21 発生）の原因構造そのものを除去する。

## 3. 方式（Drive ファイル中継）— 2026-10-22 ユーザー決定

### 3.1 全体の流れ

```
【日次・平日】
6:30 朝情報収集（Web版Work・既存）→ 朝情報.md
6:45 既存予約「日次AI現在地巡回」（Desktop版Work・1本のまま。開始時刻を 6:45 へ変更し、本文に後段を追記）：
  前段＝従来どおり現在地巡回 → AI案件_日次現在地.md
  後段＝続けて、朝情報.md＋AI案件_日次現在地.md＋Sheets今週タスクを読み、
       朝ブリーフJSONを「朝ブリーフ.json」として Drive へ保存（画面に出さない）
GAS 時間トリガー（新設・1時間おき）：朝ブリーフ.json を読み、種別を判別し、
  「朝ブリーフ」シート保存＋AI案件現在地同期（既存 saveMorningBrief の決まりのまま）
朝  ユーザー：朝ブリーフ画面を開いて見る・直す（JSONには触れない）

【週次・月曜】
5:45 週次AI巡回（Desktop版Work・既存）→ AI案件.md
週間分析JSON生成（新設予約1本）：Project「週間タスク」内の Work が
  通常業務.md＋AI案件.md＋Sheets前週実績を読み、
  週間分析JSONを「週間分析.json」として Drive へ保存
GAS 時間トリガー（新設・1時間おき）：週間分析.json を読み、種別を判別して取り込む。
  取り込んだタスク案は確定前の「案」として扱い、週間タスク画面に表示する
朝  ユーザー：週間タスク画面で候補を確認し、採用・修正・確定（確定は従来どおりユーザー）
```

### 3.2 確定事項（2026-10-22 ユーザー決定）

- JSON の置き場（2026-10-22 ユーザー決定）：GitHub ではなく Google Drive（Obsidian 連携）。保存先の具体フォルダは、実装前の静的確認で Claude Code が提示し、ユーザーの承認を得て確定する。
  - 決定の根拠：①安全（リポジトリは公開設定であり、予定・案件内容を含む JSON を置けない。Drive は本人とリンクを知る人だけ）、②実績（Work→Drive 保存は md 3本で毎日稼働中。JSON 保存も 2026-10-22 に2回実証し一字も崩れない）、③読みやすさ（取込役の GAS は同じ Google 環境の Drive を読むのが最も素直。GitHub 読取は別の認証が必要）、④一貫性（本システムは GitHub＝設計図とプログラム、Drive＝日々のデータという役割分担で構築されてきた。JSON は日々のデータ）。
  - ファイル名は `朝ブリーフ.json`（平日毎朝上書き）、`週間分析.json`（週1上書き）。日付別ファイルを増やさない（既存 md 3本と同じ上書き運用。履歴は従来どおり Sheets「朝ブリーフ」「履歴」が正データ）。
- 予約の形：朝ブリーフJSONの生成は、既存予約「日次AI現在地巡回」の後段に連結する（同一予約・同一会話内で前段→後段を続けて実行。予約は1本のまま、設定時刻は前段の開始時刻1つだけ）。失敗の切り分けは、前段の成果物（AI案件_日次現在地.md）と後段の成果物（朝ブリーフ.json）の更新有無をファイル単位で判別する。代替案（後段を独立予約に分ける）は、連結で問題が出た場合の切替先として併記しておく。
- 取込方式：朝ブリーフ・週間分析とも GAS 時間トリガーで取り込む。
- 種別の自動判別：GAS 取込時に JSON の項目で判別する。「日付」＋「今日の一言」あり→朝ブリーフ、「対象週」＋「見立て」あり→週間分析。どちらにも当たらない・両方に当たる場合は取り込まず、理由を記録する。
- 週間分析の確定：正本 v1.7「ユーザー確認は原則1回」を維持する。トリガー取込後もタスク案は確定前の「案」として扱い、採用・修正・確定は従来どおり週間タスク画面でユーザーが行う。無確認の自動確定（正本の対象外事項）はしない。「案」の保持形式は、候補専用の仮テーブルを新設しない原則（正本・v1.2）と両立する形とし、実装前の静的確認で確定して報告する。
- Work から Sheets への直接書込は新設しない（v1.2 §12 維持）。Sheets への書込は従来どおり GAS だけが行う。

### 3.3 取込処理（GAS）の要件

- 検証：既存 parseBrief／parseHandoff 相当の必須項目チェックをサーバー側に実装する。
- 二重取込防止：同じ内容（朝ブリーフは同じ日付、週間分析は同じ対象週）を二重に保存しない。取込済みの判定方法は実装前の静的確認で確定する。ユーザーが画面で修正・保存した内容を、後からの再取込で上書きしない。
- 文字の補正：JSON として解析できない場合、機械的に安全な範囲の補正（余分なバックスラッシュ・コードブロック記号の除去等）を1回だけ試み、それでも解析できなければ取込失敗とする。推測で内容を補わない。
- 失敗時の扱い：取込失敗（ファイルなし・古い日付・解析不能・検証不合格）は、朝ブリーフ画面・週間タスク画面にその旨と理由を表示する。前回値を最新として誤表示しない（IS-05 の原則）。古い日付の JSON は当日分・対象週分として取り込まない。
- 貼付欄：通常運用の経路からは外すが、画面上は「手動取込（非常用）」として残す。自動経路の障害時の代替手段とし、マニュアルにその位置づけを記す。

## 5. テスト

- 予約実行で朝ブリーフ.json・週間分析.json が所定の場所へ保存されること（上書き確認を含む）
- GAS が種別を正しく判別すること（朝ブリーフ／週間分析／どちらでもない、の3通り）
- 朝ブリーフ：トリガー取込で「朝ブリーフ」シート保存・AI案件現在地同期・履歴が、従来の貼付保存と同じ結果になること
- 週間分析：トリガー取込後、画面に「案」として表示され、採用・修正・確定・Sheets 保存が従来どおり動くこと。確定前に正データの確定タスクとして扱われないこと
- 二重取込されないこと。ユーザー修正が再取込で上書きされないこと
- 解析不能 JSON・古い日付・ファイルなしで、取込失敗が表示され、前回値が誤表示されないこと
- 非常用の手動取込が動くこと
- 既存機能（状態6値・保留・指示ルート・案件キー・複数曜日・手動追加・持越し・論理削除）の回帰がないこと
- PC／スマホ双方で表示崩れがないこと
- 自動テスト：node tests/ 全件合格（prompts.test.js は改訂後の指示文に対して）

## 6. 受入条件（ユーザー確定要求に対応）

- 平日朝、ユーザーが何もしなくても朝ブリーフ画面に当日の内容が表示され、AI案件現在地が同期されている
- 月曜朝、ユーザーが週間タスク画面を開くと候補が「案」として表示されており、確定操作だけで週が始められる
- ユーザーが JSON を作る・コピーする・貼る・目視チェックする操作が、通常運用から消えている
- 失敗時はその旨が画面で分かり、非常用の手動取込で運用を継続できる

## 7. 設計確定事項（v1.1 で確定。時刻・順序・収集の扱いはユーザー方針に影響しない設計詳細として設計側が確定）

1. 連結予約と朝情報.md の順序：連結予約「日次AI現在地巡回」の開始時刻を 6:45（朝情報 6:30 の後）へ変更する。あわせて後段の指示文に「朝情報.md の日付が当日でない場合は、朝情報抜きで朝ブリーフを生成し、JSON 内にその旨（朝情報未取得）を記録する」と書く（時刻変更と指示文の二重の守り）。
2. GAS 時間トリガー2本の実行方式：特定時刻に1回ではなく、1時間おきの実行とする。当日分（朝ブリーフ）・対象週分（週間分析）を取込済みの場合は何もしない（§3.3 の二重取込防止で担保）。古い日付・古い対象週の JSON は取り込まない。理由：日次予約に時刻ズレの実測（10/21 8:06）があり、特定時刻に賭けると取り漏らすため。
3. 週次の通常業務.md 収集：本改修では手動運用のまま変更しない。予約化は本改修の対象外とし、必要になれば別件として扱う（md 収集の決まりを変えない方針、および実装範囲を広げない原則と整合）。
