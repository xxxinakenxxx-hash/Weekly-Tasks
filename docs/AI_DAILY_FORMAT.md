# AI案件_日次現在地.md の書式（追加実装 v1.1）

根拠：docs/implementation/追加実装指示書_複数日配置・日次AI現在地連携・手動タスク追加_v1.2.md §3.2・§5・§8。

## 位置づけ
- Desktop版Workが毎朝の「日次AI現在地巡回」で作る。朝ブリーフJSON（docs/BRIEF_FORMAT.md）を作る材料としてだけ使う。
- 週次用の `AI案件.md`（docs/OBSIDIAN_FORMAT.md）の代わりには使わない。週次AI巡回は従来どおり。
- 新しいタスク候補・曜日案・優先度案・週全体の見立ては書かない（現在地だけ）。

## 保存先
- ファイル名：`AI案件_日次現在地.md`
- 保存先：Google Drive「週間タスクボード」フォルダ直下（Obsidian Vault「週間タスク」フォルダの外。Obsidianには保存しない）
- 既存ファイルがあれば上書きする（サブフォルダは作らない）。

## 書式
```markdown
# AI案件 日次現在地

取得日：2026-10-06
取得日時：2026-10-06 07:30
巡回フォルダ：C:\Users\inamori240\Documents

## 1. 案件名
- 取得日時：2026-10-06 07:28
- 台帳の最新記録日：（今の現在地として採った記録の日付 yyyy-MM-dd と見出し。2026-10-11 追加）
- 現在地：（確認できた現在工程・工程状態だけ。確認できない場合は空欄）
- 取得結果：確認済み／要確認／不一致／取得失敗／チャット未確認
- 内容：（確認済み以外の理由。不一致の場合は何と何が食い違うか）
- 確認元：
  - TASK_CURRENT.md：（ファイルの場所だけ。案件キーとして使うため、後ろに何も付けない。案件キー確認不能の場合は「なし」）
  - リポジトリ：（owner/repo。GitHub で見つかった案件、または origin を読めた案件だけ。無ければ「なし」。2026-10-15）
  - 今回読んだTASK_CURRENT.md：（今回現在地を判定した TASK_CURRENT.md の場所。案件キーとは別。読む方が変わっても案件キーは変えない）
  - 同じ案件の照合：（片方だけで発見／一致（origin＝owner/repo）／照合できない（理由））
  - 更新日時：（ローカルと GitHub の同じ案件の場合だけ。両方の更新日時と、どちらが新しいか）
  - Drive：（読んだファイル名）
  - Codexチャット：（スレッド名。特定できない場合は「チャット未確認」。Claude Code で開発している案件は「対象外（Claude Code案件）」）
  - 開発履歴：（GitHub で見つかった案件だけ。GitHub のコミット履歴）
  - 読めた経路：（GitHub で見つかった案件だけ。TASK_CURRENT.md と開発履歴を読めた経路と、失敗した経路のエラー）
```

## ルール
- 現在地の決め方と判定は、日次巡回の指示文（docs/prompts/desktop_work_ai_daily.md）の「現在地の決め方と判定」に従う（台帳の日付のあるいちばん新しい記録を今の現在地とする。古い資料との違いは不一致にしない。台帳の最新とDriveが一致すればチャット未確認でも確認済み）。2026-10-23 から、情報源が食い違う場合は日時が新しい記載を現在地に採り（判定基準 C）、実装前の案件は同じリポジトリの tasks/CHAT_CURRENT.md の冒頭定型欄（段階・現在地・最終更新）も根拠に加える（判定基準 A）。
- 案件は巡回のたびに自動で見つける（2026-10-15。docs/AI_CASES.md）。ローカルは Documents 直下の各フォルダの tasks\TASK_CURRENT.md、GitHub は所有者 xxxinakenxxx-hash のリポジトリ一覧の各デフォルトブランチの tasks/TASK_CURRENT.md。案件名・案件数・個別の場所は指示文に固定しない。
- 案件キーは案件の識別子で、今回どちらの TASK_CURRENT.md を読んだかとは別（読む方が変わっても変えない）。先に前回の結果・「タスク」シートにこの案件があるかを決め、次に有効なキー（TASK_CURRENT.md で終わる値）があるかを決める（2026-10-16。キーが無いことだけで「案件なし」としない）。有効なキーが1つなら必ず引き継ぎ、2つ以上なら要確認。同じ案件と確定する根拠は、有効なキーが今回の場所と同じか、リポジトリ（owner/repo）が同じかだけで、案件名だけでは確定しない。案件はあるがキーが空欄・不正なら、新しいキーを決めず「案件キー確認不能」（今回の場所でキーを補わない）。名前が同じ・似ている行があるだけなら「既存案件の可能性あり」として同じ案件とは確定せず、新しいキーも決めず「案件キー確認不能」。新しいキーを決めるのは、前回の結果とシートの両方を正常に確認でき、両方にこの案件そのものが無い場合だけ。どちらか一方でも確認できなければ新しいキーを決めず「案件キー確認不能」（TASK_CURRENT.md：なし、取得結果：要確認）。新しい案件は、ローカルだけなら C:\Users\inamori240\Documents\（フォルダ名）\tasks\TASK_CURRENT.md、GitHub だけ、または最初から両方なら https://github.com/xxxinakenxxx-hash/（リポジトリ名）/blob/HEAD/tasks/TASK_CURRENT.md（巡回指示文の手順 1-5）。
- 「確認元 - TASK_CURRENT.md」の場所は、その案件の「案件キー」として使う（追加改修④③。週間タスクの「案件キー」列、朝ブリーフJSONの「案件キー」と同じ値）。場所は一字も変えずに書く。
- 「TASK_CURRENT.md：」の行には場所だけを書き、後ろに読めた経路・Cache miss・取得失敗・取得方法・注記を付けない（2026-10-14：10/14 にこの行へ経路の説明が付き、朝ブリーフJSONの案件キーに混入した）。経路とエラーは「読めた経路：」、その他の注記は「内容」に書く。
- 現在地は確認できた事実だけを書き、推測で補わない。
- 「不一致」は、台帳のいちばん新しい記録と同じ時点かそれより新しい資料が別の内容を示す場合だけ。古い資料・台帳内の古い記載との違いは不一致にしない（2026-10-11）。2026-10-23 から、日時で新旧を決められる食い違いは新しい記載を採り（注記に「食い違い検出：…」）、「不一致／要確認」にするのは、日時がどの情報源からも取れない場合、または最も新しい記載が同時刻で中身が違う場合だけ。
- 読めなかった情報源がある場合は「取得失敗」、対応するCodexチャットを特定できない場合は「チャット未確認」、判断できない場合は「要確認」とする。
- 一部の案件だけ取得できない場合も、取得できた案件は「確認済み」として書く（案件ごとに扱う）。
- 巡回そのものに失敗した場合も、分かる範囲で「取得失敗」と書いて保存する（前日のファイルを残したまま当日分として扱わせない）。
- ChatGPT Project は、取得日が当日でないファイルを当日の取得として扱わない（取得失敗／前回値）。
